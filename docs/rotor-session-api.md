# Сессионный rotor-API Яндекс.Музыки

Протокол, которым пользуется официальное десктопное приложение
(`YandexMusic/5.114.1`, Electron 38). Восстановлен 6 сентября 2026 из бандла
приложения (`resources/app.asar`) и **проверен вживую** на боевом API.

Бот переведён на этот протокол 6 сентября 2026. «Классический» ротор
(`/rotor/station/<станция>/tracks` + `/feedback`) не исчез и продолжает
отвечать `200`, но идентификатора сеанса в нём нет, а приложение давно
работает через сессионный — именно в нём у прослушивания есть
идентификатор, к которому привязываются все оценки.

## Зачем это нужно

У классического ротора нет идентификатора сеанса: максимум, что связывает
фидбек с выдачей, — `batch-id` очередной пачки. В сессионном API появляется
`radioSessionId`, и сервер понимает, какую именно волну правит очередной
скип или дизлайк.

## Идентификатор сессии

`radioSessionId` — строка вида `52Aj-bdctPL0vlCssal-5itl`. Живёт с момента
создания сессии до её конца, `batchId` внутри неё меняется на каждой пачке.

## Эндпоинты

Базовый адрес — `https://api.music.yandex.net`.

| Метод и путь | Назначение |
| --- | --- |
| `POST /rotor/session/new` | создать сессию |
| `POST /rotor/session/<sid>/tracks` | следующая пачка треков |
| `POST /rotor/session/<sid>/clone` | клонировать сессию |
| `POST /rotor/session/<sid>/feedback/` | один фидбек |
| `POST /rotor/session/<sid>/feedbacks/` | пачка фидбеков |
| `POST /rotor/sessions/feedbacks/` | фидбеки сразу по нескольким сессиям |
| `GET /rotor/wave/last` | последняя волна пользователя |
| `GET /rotor/wave/settings?seeds=…` | настройки волны для набора seed'ов |
| `POST /rotor/wave/last/reset` | сбросить последнюю волну |

**Завершающий слэш у путей фидбека обязателен.** Без него сервер не отвечает
`404`, а обрывает соединение (`ConnectionError`/`RemoteDisconnected`) — на
это легко потратить много времени, приняв обрыв за сетевую проблему.
`GET` на эти пути даёт `405`, то есть маршрут существует и ждёт `POST`.

## Создание сессии

```jsonc
POST /rotor/session/new
{
  "seeds": ["track:20599729"],      // "user:onyourwave" — обычная «Моя волна»
  "includeTracksInResponse": true,
  "trackToStartFrom": "20599729"    // необязателен, см. ниже
}
```

Ответ: `radioSessionId`, `batchId`, `acceptedSeeds`, `descriptionSeed`,
`pumpkin` и `sequence` — список элементов с полями `track`, `liked`,
`trackParameters` (`bpm`, `energy`, `hue`, `mixFade`).

Приложение умеет передавать также `queue`, `clientRemoteType`, `incognito`,
`child`, `allowExplicit`, `aliceExperiments`, `djData`, `useIchwill`,
`includeWaveModel`, `interactive` и `sessions` (список
`{sessionId, seeds, feedbacks}` — так переносятся оценки из прошлых сессий).

### Волна от конкретного трека

По кнопке «Моя волна» на треке приложение отправляет `seeds: ["track:<id>"]`
и **не передаёт** `trackToStartFrom` — это видно в дампе трафика. Первым в
`sequence` при этом приходит не сам трек-семя, а похожий на него.

Параметр `trackToStartFrom` в API тем не менее существует и работает:
проверено на живом API — с ним запрошенный трек становится **первым** в
`sequence`. Если нужно, чтобы волна началась именно с выбранного трека, это
рабочий способ, просто приложение идёт другим путём (сам трек оно уже играет
локально, а у волны просит продолжение).

Тот же сценарий доступен и на классическом роторе — станция `track:<id>`
отвечает и на `/info`, и на `/tracks?settings2=True`, — но там нельзя
попросить начать именно с этого трека.

## Фидбек

Подлинный запрос приложения из дампа трафика:

```jsonc
POST /rotor/session/<sid>/feedback/
{
  "event": {
    "type": "trackStarted",
    "timestamp": "2026-09-06T18:32:51.003Z",
    "trackId": "138294733:36264233"
  },
  "batchId": "d18e2432-c6f1-46b1-9379-3ffe0bf2d4a3.eAWL",
  "from": "desktop-wave_landing_screen-my_wave-radio-default"
}
```

Обратите внимание: полезная нагрузка лежит во вложенном объекте **`event`**,
а `batchId` и `from` — соседи `event`, а не его поля. В классическом роторе
`type`/`timestamp`/`trackId` лежали на верхнем уровне, а `batch-id` был
query-параметром. Пачка фидбеков уходит на `POST …/feedbacks/` с обёрткой
`{"feedbacks": [ … ]}`, одиночный `POST …/feedback/` — таким же объектом без
обёртки.

Три поля легко сделать неправильно, и сервер об этом не скажет — на любой из
этих ошибок он отвечает `200`:

- **`trackId` составной: `"<id трека>:<id альбома>"`.** В ответе сервера это
  `track.id` и `track.albums[0].id`. Голый id трека сервер принимает, но,
  судя по всему, не сопоставляет.
- **`timestamp` — строка ISO-8601 в UTC с суффиксом `Z`** и миллисекундами
  (`"2026-09-06T18:32:51.003Z"`), а не число Unix-времени. Учтите, что
  `datetime.isoformat()` в Python даёт `+00:00` и микросекунды.
- **`from` — строка контекста запуска**, например
  `desktop-wave_landing_screen-my_wave-radio-default` для «Моей волны» или
  `desktop-radio-track-178500-default` для волны от трека. Приложение
  передаёт её всегда. У `radioStarted` она дублируется и внутри `event`, и
  снаружи, а `batchId` при этом не передаётся вовсе.

Состав `event` по типам (как его собирает приложение):

- `radioStarted` — `type`, `timestamp`;
- `trackStarted`, `like`, `unlike`, `undislike` — плюс `trackId`;
- `skip`, `dislike` — плюс `trackId`, `totalPlayedSeconds`;
- `trackFinished` — плюс `trackId`, `totalPlayedSeconds`, `trackLengthSeconds`.

Полный список типов из бандла: `radioStarted`, `trackStarted`,
`trackFinished`, `skip`, `skipFailed`, `like`, `dislike`, `ad`, `jingle`,
`unlike`, `undislike`, `combinedQueueStarted` и семейство
`playableItem*` (для не-музыкальных сущностей).

**`like` и `dislike` здесь — типы фидбека ротора.** То есть волне можно
сказать «такое мне не нравится» сигналом заметно более сильным, чем скип, не
трогая коллекцию пользователя.

## Фидбеки вместе с запросом треков

Главная особенность, которой нет в классическом роторе. Подлинный запрос
приложения при пропуске трека:

```jsonc
POST /rotor/session/<sid>/tracks
{
  "queue": ["139047702:36575712", "138294733:36264233"],
  "feedbacks": [{
    "batchId": "d18e2432-c6f1-46b1-9379-3ffe0bf2d4a3.eAWL",
    "event": {
      "type": "skip",
      "timestamp": "2026-09-06T18:32:50.733Z",
      "trackId": "139047702:36575712",
      "totalPlayedSeconds": 22.435
    },
    "from": "desktop-wave_landing_screen-my_wave-radio-default"
  }]
}
```

Оценки уходят **тем же запросом**, которым запрашивается следующая пачка, —
сервер учитывает их при подборе и сразу возвращает новый `batchId`. При
раздельной отправке гонка неизбежна: пачка может быть подобрана раньше, чем
доедет скип.

В `queue` приложение передаёт **два** идентификатора в том же составном
формате: трек, по которому только что ушёл фидбек, и следующий за ним — тот,
что уже стоит в очереди на воспроизведение.

Наш бот в `queue` шлёт **один** идентификатор, и это не баг: у приложения
локальная очередь воспроизведения глубже — оно знает и текущий трек, и
следующий, — а наш буфер (`WaveSession`, `MAX_BUFFERED_TRACKS`) сознательно
держит только один трек за раз, который к моменту этого запроса уже
выдан и вычищен из буфера. Сообщить второй идентификатор нам в этот момент
физически нечем (см. `bot/yandex/wave.py::WaveSession._build_queue`).

Сразу после получения новой пачки приложение отдельным запросом
`POST …/feedback/` отправляет `trackStarted` по треку, который начал играть.
То есть на каждый пропуск приходится пара запросов: сначала `tracks` с
`skip` внутри, через доли секунды — `feedback/` с `trackStarted`.

Наш бот `trackStarted` отдельным запросом не шлёт: он кладёт фидбек в
очередь и досылает его вместе со следующим запросом пачки (тем же путём, что
и `skip`) — так же, как поступает с остальным фидбеком между запросами
пачек. Ничего не теряется: время события фиксируется в момент постановки в
очередь, а не в момент отправки, а сама очередь принудительно досылается
(`flush_pending_feedbacks`) перед тем, как сессию заменят или отключат, так
что фидбек не может застрять в объекте, который вот-вот выбросят.

## Смена волны

Когда пользователь запускает другую волну, приложение перед созданием новой
сессии досылает накопленный фидбек старой — обе операции уходят в одну и ту
же миллисекунду:

```jsonc
POST /rotor/sessions/feedbacks/
{ "sessions": [ { "sessionId": "<старый sid>", "seeds": ["user:onyourwave"], "feedbacks": [ … ] } ] }

POST /rotor/session/new
{ "seeds": ["track:178500"], "includeTracksInResponse": true, "includeWaveModel": true, "interactive": true }
```

Обратите внимание: для волны от трека приложение передаёт **только** `seeds`
и не использует `trackToStartFrom` — хотя этот параметр в API существует и
работает (см. выше). Сразу после создания сессии уходит `radioStarted`.
