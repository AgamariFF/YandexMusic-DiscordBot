# Шифрованный сокет nekto.me («e-socket»)

Сервис перевёл прикладные сообщения сокета на шифрование. Открытый JSON,
по которому написана первая версия `bot/nekto/`, сервер больше не принимает:
он молча не отвечает на `register`, и рукопожатие виснет по таймауту.

Схема восстановлена 10 сентября 2026 из бандла аудиочата
(`https://nekto.me/audiochat/js/app.<hash>.js`, модуль `8b2e`). Бандл
обфусцирован массивом строк с ротацией — деобфускация описана в конце.

**Проверено вживую** в тот же день: с реальным токеном рукопожатие проходит
целиком — зашифрованный `register` принят, сервер ответил зашифрованным
пакетом, сессионный ключ получен, `web-agent` ушёл уже им, после чего сервис
начал слать данные (`users-count`), и они расшифровываются. Отдельно важно:
**отпечаток браузера для входа не требуется** — рядом с шифрованием в бандле
лежит слой фингерпринтинга (`canvas`, `webglInfo`, `gumHash`, `deviceInfo`,
`challenge-trace`), но сервер пустил клиента без него.

## Алгоритм

Ключ выводится хешированием секрета, шифрование — AES-GCM:

```
ключ      = SHA-256( UTF-8(секрет) )        // 32 байта, importKey("raw", …)
IV        = 12 случайных байт
шифротекст = AES-GCM( ключ, IV, UTF-8( JSON(сообщение) ) )
```

WebCrypto дописывает 16-байтовый тег аутентификации в конец шифротекста —
Python-реализации (`cryptography`, `pycryptodome`) делают так же, поэтому
дополнительной работы с тегом не нужно.

## Формат пакета

```jsonc
{
  "s": "<base64 шифротекста>",
  "i": "<base64 IV>",
  "_": 1            // режим: каким ключом зашифровано
}
```

Имена полей односимвольные и неочевидные: `s` — payload, `i` — IV,
`_` — режим. При расшифровке клиент проверяет, что `s` и `i` — строки, иначе
бросает `e-socket payload is incomplete`.

## Два ключа и два режима

| Режим | Ключ | Чем шифруется |
| --- | --- | --- |
| `2` | секрет, зашитый в бандле | единственное сообщение `register` |
| `1` | сессионный ключ от сервера | все остальные сообщения |

Порядок:

1. Клиент шифрует `register` **зашитым** секретом и шлёт с `"_": 2`.
2. Сервер отвечает сообщением `type: "registered"`, в котором поле `s` —
   не шифротекст, а **сам сессионный ключ строкой**. Клиент проверяет это
   отдельно (`type === "registered" && typeof s === "string" && s.length`).
3. Дальше всё шифруется сессионным ключом с `"_": 1`.

Пока сессионный ключ не получен, исходящие сообщения копятся в очереди и
отправляются, когда ключ появится, — иначе первые сообщения ушли бы
незашифрованными.

Зашитый секрет на 10 сентября 2026:

```
e723938b821ede7337fbe5e642693d1d9474d5bedfdcd01039693e38d424fc72
```

**Это самая хрупкая часть.** Секрет живёт в бандле фронтенда и меняется
вместе с ним: после очередного релиза сервиса вход отвалится ровно так же,
как отвалился открытый протокол. Тогда его нужно достать заново — см. ниже.

## Как достать секрет заново

1. Скачать бандл аудиочата: ссылка на `app.<hash>.js` есть в разметке
   `https://nekto.me/audiochat`.
2. Найти в нём маркер `e-socket payload is incomplete` — рядом лежит модуль
   шифрования.
3. В начале модуля объявлены две константы: режим (`"1"`) и сам секрет —
   строка из 64 hex-символов.

Строки в модуле спрятаны в массив, а индексы смещены; вдобавок массив
**ротируется** самовызывающейся функцией, пока контрольная сумма не сойдётся
с зашитым числом. Без эмуляции этой ротации индексы указывают не на те
строки. Рабочий деобфускатор — в истории обсуждения; принцип: считать
контрольную сумму по той же формуле, что в IIFE, и крутить массив
(`push(shift())`), пока она не совпадёт.

## Что это меняет для бота

Меняется только транспорт: `bot/nekto/transport.py` шифрует исходящие
сообщения и расшифровывает входящие. Сам состав сообщений — `register`,
`web-agent`, `scan-for-peer`, события `peer-connect`/`offer`/`answer` и
прочее — не изменился и описан в docstring'ах `bot/nekto/protocol.py`.
Шифруется оболочка, а не содержимое.
